# INPUT — the knowledge graph

`hyp_gen` reads exactly one JSON file: a literature knowledge graph. Everything
it can ever say comes from this file. If a fact is not here, it cannot appear
in a hypothesis, and that is the property that makes the output checkable.

A graph is: **things** (entities), **links** between them, **findings** that
back each link with a verbatim sentence, the **papers** those sentences came
from, **gaps** the builder flagged, and a **coverage** block saying how hard it
looked.

The three fields this app leans on hardest, and why:

- **`coverage`** — depth, how much of what was found was actually read, and
  whether the search truncated. Novelty that rests on "nobody has said this"
  is scaled by these numbers, and at `quick` depth the scaling factor is zero.
  Page one lies; a shallow search is not evidence of absence.
- **`findings`** — each carries a verbatim sentence, its paper, and whether it
  argues **for**, **against**, or for **no effect**. Support is recomputed from
  these rather than trusted from `links.confidence`, so a link asserting 0.9
  with one hedged preprint behind it will not score like one with two
  independent groups.
- **`links.where`** — the conditions a result was measured under. A link whose
  findings disagree is usually two experimental conditions rather than a
  conflict, which is why reconciling one is a first-class hypothesis here
  rather than a data-quality complaint.

Unknown fields are preserved rather than rejected: the graph builder owns this
schema and will grow it, and a new key upstream is not a reason for this app to
stop working.

Machine-readable form: [`schemas/knowledge-graph.schema.json`](../../schemas/knowledge-graph.schema.json).
